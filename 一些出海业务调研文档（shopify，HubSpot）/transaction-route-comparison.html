1. 结论与选择建议

按当前项目状态，建议先用方案一跑通真实业务；长期的服务型业务可以迁移到方案二。

当前落地优先

方案一：Shopify 下单 + HubSpot 管理

付款、退款和客户订单链接已经验证，近期上线风险更低。HubSpot 负责 Deal、Ticket、Task 和余额摘要。

长期服务型方向

方案二：HubSpot 产品 + Deal + Payment Link

系统更集中，适合医疗服务和医旅定制；但需要 Stripe 审核、相关 HubSpot 套餐，以及消费者服务页面开发。

无论选哪套：消费者只读服务进度；CMT 客服或系统更新状态。余额不能只靠 Deal 或订单金额推算，必须由受控财务流水计算，再将余额和预警结果同步到 HubSpot。

3. 服务进度如何管理

一笔交易可以包含多个虚拟服务，但“买了什么”和“服务做到哪一步”是两类数据，不能只用订单或产品明细代替履约记录。

推荐的数据结构

Deal整笔定制交易、总金额、付款结果和余额摘要
Line Item购买了哪些服务、数量和价格，可增加“服务状态”作为辅助
Ticket每个服务的负责人、阶段、备注、时间线和完成记录
Task服务下的具体待办，例如资料收集、预约确认、回访提醒

服务状态示例

待开始已付款，尚未启动该服务
资料准备等待客户资料或内部核验
进行中客服或服务团队正在执行
待确认等待 CMT 内部确认结果
已完成服务交付完成，允许按规则完成扣费
关于“一条 Ticket + 多个 Task”：这种方式适合内部轻量跟进；但如果要分别展示“服务1完成、服务2进行中”，建议每个服务一条 Ticket。消费者只读 Ticket 对应的进度，不能直接修改状态。
Shopify 和 HubSpot 的共同限制：Shopify 的 Fulfillment 状态、HubSpot 的 Line Item 状态，都不等同于“医院已预约、行前准备中、服务执行中”等 Medora 业务进度。正式状态应由 Ticket 或独立服务记录承载。

4. 余额与扣费如何运作

预付款账户财务工具保存逐笔充值、扣费、退款和凭证
→
扣费确认服务达到规定节点后，由 CMT/财务确认可扣金额
→
HubSpot Deal保存余额汇总、状态和最近对账时间

当前余额 = 累计预付款 + 累计补款 − 累计已确认支出 − 累计退款

扣费触发

不是客户自行点击完成，也不是 Shopify/HubSpot 自动发货。由服务 Ticket 达到规定阶段后，CMT 或财务确认扣费。

余额更新

财务工具完成流水后，把累计预付款、累计支出、累计退款、余额和最近对账时间回填 HubSpot。

余额预警

余额低于阈值时创建 Task、通知负责人，并向客户发送补款或续费链接。

必须保留的边界：HubSpot 只保存汇总和业务状态，不作为逐笔资金台账。每笔扣费要有服务、金额、时间、凭证和操作人/系统来源，避免重复扣费。

6. 两套方案的完整流程

方案一：Shopify 下单 + HubSpot 管理

1HubSpot 建 Contact / Deal记录客户和本次定制服务
2Shopify 建商品/订单Draft Order 包含多个虚拟服务
3客户付款Shopify Order 记录 Paid
4创建服务 Ticket每项服务一条，分别推进
5扣费与余额财务记录后回填 HubSpot
关键开发：Shopify Order paid 事件通过订单 ID/Deal ID 匹配 HubSpot；不能只依赖姓名或邮箱。订单同步后，仍要把每个服务映射到 Ticket，Shopify 拆分履约状态不会自动成为 Medora 服务状态。

方案二：HubSpot 产品 + Deal + Payment Link

1HubSpot 建 Product建立服务名称、价格和 SKU
2创建 Deal关联 Contact 和多个 Line Item
3生成 Payment Link客户直接在 HubSpot/Stripe 页面付款
4创建服务 Ticket每项服务一条，分别推进
5扣费与余额财务记录后回填 HubSpot
关键前提：必须先完成 Stripe 收款账户注册与审核；Payment Link 解决的是收款，不会自动产生消费者订单中心，也不会自动创建完整的服务履约记录。

8. 实施准备与验收

第一阶段

先跑通当前方案

用 Shopify 完成一笔多服务定制订单；HubSpot 关联 Contact、Deal 和服务 Ticket，手动更新各服务状态。

第二阶段

建立余额规则

明确每个服务节点的扣费金额、凭证要求、余额阈值、补款方式和退款规则。

第三阶段

再评估迁移 HubSpot

Stripe 审核通过且套餐成本可接受后，用同一套服务 Ticket 和余额规则切换付款入口。

正式上线前必须验证

  • 付款成功后，正确匹配 Contact 和 Deal，不重复创建交易。
  • 一笔交易的多个服务可以分别建立 Ticket，并分别更新状态。
  • 服务状态变化有负责人、时间线和操作记录。
  • 扣费只在规定节点确认后发生，重复回调不会重复扣费。
  • 余额低于阈值时生成提醒，并能向客户提供补款入口。
  • 消费者只能查看状态和余额，不能直接修改履约状态。
  • 消费者页面不展示诊断、病历、检查报告或其他敏感临床信息。
推荐最终架构：Deal 管整笔交易，Line Item 记录购买服务，Ticket 管每项服务进度，财务工具管逐笔资金流水，Medora 自建页面向消费者只读展示服务状态和当前余额。

能力参考：HubSpot Payment Links、HubSpot Line Items、HubSpot Customer Portal、Shopify Payments 费用。实际可用套餐、支付资质、费率和权限以客户账户最终显示为准。

本页面只表达当前确认的业务方案，不包含讨论过程。支付、税务、退款、隐私和跨境合规仍需由客户、财务及法务最终确认。
